# 售后 Agent 评测数据集

数据集版本：2026-10-27，第一版扩充。

样本按用途放在三个 JSON 文件中，本文件集中说明字段、划分和运行方法。JSON 可以被脚本直接读取，也可以在编辑器中逐条查看。

这些是按项目当前分类约定、知识文档与业务规则编写的合成样本，尚未经过独立人工复核，也不是采集到的真实客户日志。相近改写保存在同一分组；条目数量与独立场景数量分别统计。

## 文件和规模

| 文件 | 条目数 | 划分 | 用途 |
|---|---:|---|---|
| `backend/data/intent_cases.json` | 272 | 开发 104，测试 168 | 查询、退款、换货、待澄清四分类 |
| `backend/data/retrieval_cases.json` | 200 | 开发 24，校准 50，测试 126 | 检索命中、证据不足与商品范围 |
| `backend/data/after_sales_cases.json` | 40 | 当前能力 36，改进目标 4 | 36 条可自动回放的业务场景，以及 4 条已知能力缺口 |

意图开发集包含原 32 条冒烟题，以及新增的 24 组、每组 3 种表达；测试集包含另外 56 组、每组 3 种表达，四类各 42 条。新增部分共 80 个编写场景，不能把 240 种表达都当成互相独立的场景。

检索开发集保留原 C01—C08、E01—E16 共 24 条旧题；它们已经参与过早期调试，不再作为新留出测试成绩。新校准集为 24 条有答案题、26 条无答案题；新测试集为 64 条有答案题、62 条无答案题。新增改写每组两条；相同尺码表及申请计时规则的相关题进一步归入共同分组。

## 样本字段

三个文件都有以下字段：

- `id`：稳定的样本标识，报告用它定位错题。
- `group`：同一编写场景或事实主题的分组；同一组全部属于同一集合。
- `split`：`development` 用于调试，`calibration` 用于选阈值，`evaluation` 用于测试。
- `rationale`：预期标签或依据的说明，便于逐条复核。
- `origin`：`authored` 为本轮新增，`legacy_smoke`、`legacy_retrieval` 为旧题。

意图样本还包含：

- `history`：用户与客服的历史消息，带 `role` 和 `content`。
- `text`：本轮用户消息。
- `expected_intent`：预期的四分类标签。
- `category`：资格咨询、改口、短确认、缺订单号等编写主题。

意图标签按本轮诉求确定。`query` 包括咨询、暂缓和否定办理；`refund`、`exchange` 表示明确委托对应操作；`clarify` 表示已要求办理，但退款和换货仍未选定。缺少订单号或材料，属于后续业务补充，不自动变为 `clarify`。请求他人订单退款仍可归 `refund`，服务端应另外拒绝越权。

历史在数据里保留完整编写内容，运行时交给真实分类器处理，因此仍执行当前“最多四条历史消息、每条取末尾 600 字符”的输入限制。分类样本不是用户确认记录，也不会替代业务授权。

检索样本还包含：

- `query`、`model_code`、`category`：问题与可信商品范围。
- `expected_document_id`、`expected_text`：预期文档与其中的原文依据。无答案题的文档标识为 `null`。
- `negative_kind`：`missing_fact` 为所问具体事实缺资料，`unknown_model` 为未知型号，`scope_mismatch` 为型号品类错配，`off_topic` 为范围外问题。

无答案题重点增加了同型号的具体参数缺失，例如耳机单元尺寸、续航数值、服装未收录的袖长和尺码。资料中已经明确说明某项功能或参数未提供的题，也有相应有依据题，用于检查能否引用证据解释边界。

业务样本还包含：

- `setup`：虚构订单、客户、金额、工单状态和故障前提。`{order}`、`{ticket}` 等是回放时需替换的占位符。
- `steps`：客户对话或管理员、系统操作，包括关注的工具与禁止的工具。
- `expected`：退款标志、成功记录数量上限、允许的工单状态，以及具体核验要点。`ticket_status_in` 非空时要求有对应工单；`allow_no_ticket` 允许材料不足时先追问、不创建工单。
- `suite`：`current` 对应现有业务约定，`target` 对应尚待实现的改进。
- `known_gap`：目标场景的现有缺口；B-037—B-040 均涉及独立用户确认机制。
- `execution`：固定为 `scenario_spec`，表示数据采用操作步骤和断言的场景规范格式。

`python -m scripts.business_eval --live` 读取其中的 36 条 current 场景，调用真实统一聊天图或审批 API；4 条 target 场景单独写入报告的 `known_gaps`，不计通过。原 `python -m evals.run` 仍然运行基础退款回归，不读取这个新文件。离线校验只验证结构与工具名。

## 离线校验

在 `backend` 目录中，使用项目虚拟环境运行：

```bash
python -m evals.datasets
python -m pytest tests/test_eval_datasets.py -q
```

校验包括字段和标签、重复 ID、重复输入、同组跨集合、正例的知识原文和商品范围。对于业务场景，还核对工具名以及当前能力与目标场景的区分。

重复检查可以发现相同输入和显式分组泄漏；语义近似仍需人工抽查。正例原文存在表示已标注片段确实收录，不能据此自动证明负例标签和所有业务断言都正确。

## 意图分类评测

```bash
# 保留原命令行为：仅运行原 32 条冒烟题
python -m scripts.intent_smoke --live

# 开发集用于调试
python -m scripts.intent_smoke --live --split development --out var/intent-development.json

# 固定测试集单独记录，不与开发集成绩混合
python -m scripts.intent_smoke --live --split evaluation --out var/intent-evaluation.json
```

默认只调用本地配置的 Ollama，不调用商城工具和业务数据库。`--limit N` 可用于排查少量样本，报告会记录限制；限量结果不能作为完整集合成绩。

报告保存样本 ID、实际标签、分类来源、降级原因和耗时，并记录数据文件与分类器源码的 SHA-256 指纹。相同指纹可用于确认两次运行使用相同的数据和实现。

核心指标：

- `label_accuracy`：整条分类链路的正确比例，包括规则降级的结果。
- `model_only_accuracy`、`model_coverage`：模型正常给出标签时的正确比例，以及这部分占全部请求的比例；没有模型结果时准确率记为 `null`。
- `confusion_matrix`、`per_class`：各类错分去向、精确率和召回率。
- `unsafe_write_rate`：预期为查询或待澄清，却被预测为退款或换货的比例。它衡量错误开放写工具的风险，不等于已经执行了退款。

命令只有在所有样本都由模型完成并分类正确时返回 0。脚本契约测试可以使用模拟输出，它们不构成 Qwen 准确率成绩。

## 检索校准和测试

下面两条命令会真实调用配置的百炼与 Qdrant，并消耗外部服务额度：

```bash
python -m app.rag.evaluate --live --calibrate --out var/retrieval-expanded-calibration.json
python -m app.rag.evaluate --live --out var/retrieval-expanded-evaluation.json

# 使用上述校准报告的阈值做对照，不修改 .env
python -m app.rag.evaluate --live --thresholds-from var/retrieval-expanded-calibration.json --concurrency 3 --out var/retrieval-calibrated-evaluation.json
```

先用校准集选阈值，再把确定的配置用于测试集。校准命令只输出建议值，不自动改 `.env`。读取校准报告时，脚本核对数据指纹、知识版本与 Embedding 配置，仅在本次运行的配置副本中覆盖阈值。当前项目配置保留旧阈值，本次真实对照成绩单独记录。

`--concurrency` 控制同时处理的问题数，默认 1，上限 8。同一问题的各模式依次执行，各模式共享一次真实查询向量；报告记录并发数。不同并发条件下的耗时不作严格性能比较。

测试报告记录 Hit@1/4、无答案放行率、有答案误拒率、引用有效性、跨型号误检、服务异常与重排降级。无答案放行指检索层返回了候选证据；生成模型仍可能识别资料边界，因此不能直接把该指标叫作幻觉率。服务不可用单独计为错误，不与证据不足混合。

同一批 126 条测试问题分别运行 Dense、Hybrid、Hybrid+Rerank，仍是 126 个问题，不是 378 个独立问题。报告中的 `dataset_cases` 和数据指纹明确记录本次集合。

## 真实业务回放

```bash
python -m scripts.business_eval --live --out var/business-evaluation.json

# 排查单条或多条场景
python -m scripts.business_eval --live --case B-018 --case B-019 --out var/business-selected.json
```

命令连接已配置的 PostgreSQL 服务，在 `postgres` 管理库连接上新建随机命名的 `aster_eval_<随机串>` 数据库。账号需要创建数据库的权限。所有业务表、退款记录、工单、审批和 Checkpoint 都在这个新库中运行；正常完成或执行异常后，程序删除自己本次创建的临时库。已有演示库不参与回放。

聊天步骤使用真实 Qwen、DeepSeek、百炼和 Qdrant。MCP 使用真实 SDK 和服务器代码，通过进程内 ASGI 传输，不要求另起服务端口。Redis 使用 fakeredis，未验证真实 Redis 的跨进程锁或网络故障。重启场景重建工作流图、Saver 和连接池，保留同一个真实 PostgreSQL 测试库；未模拟操作系统强制断电。

自动断言检查预期/禁止工具、API 权限、退款标记、工单状态、成功记录上限、退款与受理互斥、受理编号及部分专用条件。`prose_checks_for_review` 保存需要另看回复与证据的文字要点；自动状态断言通过不表示所有回复都已通过语义质量评判。

响应丢失场景在服务端完成真实测试库写入后，向 Agent 注入 `OUTCOME_UNKNOWN`；知识故障场景注入不可用结果。报告保留这些故障前提。4 条用户确认目标场景未实现，不以模拟成功填充。

普通 `pytest` 默认跳过这组真实回放，避免日常检查产生模型费用。显式入口要求临时库名称满足固定随机格式；真实回放日志和逐条 JSON 保存在忽略的 `backend/var/`，不进入普通源码提交。

## 使用与维护约定

### 最终知识回答

```bash
python -m scripts.answer_eval --live --split development --out var/answer-development.json
python -m scripts.answer_eval --live --out var/answer-evaluation.json
python -m scripts.answer_eval --live --case R-N-29-1 --out var/answer-selected.json
```

此命令运行真实 Hybrid + Rerank，并将实际检索内容交给生产代码中的证据回答函数。回答拆成有原文支持的事实和仍缺失的事项；程序校验文档、版本、片段、原文引用和数字，然后组装最终回复。格式或引用校验失败时最多修正一次，所有生成调用通过同一用量入口计数。无需操作业务数据库。

正例自动判断是否采用预期文档的依据作答，负例检查是否说明资料不足；服务故障与证据不足分别记录。这个指标衡量回答/拒答与依据范围，逐句语义仍需检查，报告不将它称为人工答案正确率。原文定位和数字核验也只覆盖对应的一致性边界。检索阈值保持原配置。

### 分类保护与新增题

```bash
python -m scripts.intent_smoke --live --split evaluation --dataset data/intent_holdout_cases.json --out var/intent-additional.json
```

原有 272 题保持原样，另存 48 条新措辞题，每类 12 条。新增题在实现冻结后运行；自建题仍需持续补充实际对话，并单独报告其分布和失败情况。

分类结果新增 `model_intent` 和 `guard_reason`。模型原始预测、应用保护后的分类分别计分；当客户在两个方案之间尚未选择，程序将办理分类收紧为澄清，聊天和 MCP 复用收紧后的结果。`model_only_accuracy` 按模型原始预测计算，`label_accuracy` 按最终分类计算。模型不可用或输出非法时仍使用原有规则降级，按 `fallback_count` 单列。

2026-10-28 已增加持久化退款确认单、10 分钟有效期和独立客户确认接口。普通退款、大额转人工及退款后再查询等业务样本增加 `confirm_refund` 步骤，通过客户身份调用确认 API。B-037～B-040 尚未接入此真实模型回放器，其取消、过期、身份与快照绑定、重放、并发和回滚机制由 `tests/test_refund_confirmation.py` 独立覆盖，并在真实 PostgreSQL 下通过 18 项测试，包含人工审核资格变化及处理方式变更的复核。此次仅复跑 B-008 和 B-016，历史 36/36 不作为新版本全量成绩。

旧版 `evals.run` 退款基准在收到确认单后显式模拟客户点击，并将动作单独写入回放，以继续检查完整业务结果。这个客户模拟只用于该基准；生产 Agent 和授权安全测试均不自动确认。

- 调整提示词主要看开发集；最终测试集用于固定版本的成绩报告。根据测试错题继续修改后，应承认该测试集已经参与开发，并在后续补充新的留出题。
- 样本改写保留同组划分。增加样本时先核对知识原文与业务规则，不按期望的漂亮分数改标签。
- 负例优先复核同型号相似问题。多个问题涉及相同事实时，应检查是否需要合并分组。
- 知识内容、Embedding、分词或 BM25 索引发生变化时，重新核对依据并校准；旧报告只代表其记录的数据、知识版本和配置。
- 本次真实测试的成绩和发现的问题见[评测结果](评测结果-20261027.md)。离线回归与真实模型成绩分别记录。
- 本轮修正与后续实测见[修复复测](修复复测-20261027.md)。历史报告与中间失败结果均保留。
